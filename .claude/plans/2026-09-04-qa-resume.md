## #401 closed — `e8345da`

The two remaining acceptances. The reply window is now
`min(created + 7 days, universallyPastFrom(eventDate))` — the instant
`isUniversallyPastDate` starts returning true, which is the instant `accept`
starts refusing, so a request can never be live while unacceptable. Migration
`0022` pulls every **live** row back, because the acceptance is a property of
the data and not of the writer; the local database held the exact reported row
(event Aug 31, `expires_at` Sep 7) and now holds Sep 2. The request page calls
`requireRole('customer')` instead of hand-bouncing vendors only.

The ticket's own Tests line asked for `min(created + 7 days, event date)`, which
is unimplementable: the event date's midnight has already passed for a request
sent *for today*, which the product allows, so it would expire a same-day
request at birth. The deviation, and two consequences signed off consciously —
the vendor being told to "Reply by September 8" for a September 7 event, and
the deliberate absence of a floor on the window — are recorded in #401's detail
section so a later sweep lands there rather than refiling them.

### What capping the window broke, and this fixed with it

Three surfaces stated a deadline the product no longer grants:

- The vendor's `new_request` notification stored a **countdown**. That body is
  rendered verbatim by the bell and the email for the life of the row, so
  "expires in 5d" would sit in the vendor's inbox four days later beside a
  queue row reading "expires today" — the two-voices defect displaced in time
  rather than removed. It stores a **date** now.
- The expiry notification claimed "It went unanswered for a week".
- The success panel promised a flat seven days, twice, after the row existed.

`bookingRequestWindowPhrase` is **deleted**: with a per-row deadline there is no
flat window to state, and an exported helper left in place reads as the
sanctioned way to state one. Its last caller was the pre-submission rail, which
now drops the duration rather than computing one from a clock it would disagree
with the server about — it is a client component that still server-renders.

**On the rendering test, a caveat worth keeping.** jsdom cannot reproduce the
JSON-LD breakout: React writes the block by setting `innerHTML` on a `<script>`
element, and the fragment parser runs in text mode for a script context, so a
raw `</script>` becomes text and builds nothing. The obvious version of this
test is therefore **green against the vulnerable code**. The assertion that
carries acceptance 2 renders to markup and re-parses it through a *document*
parser, which is the path a browser takes; against a `JSON.stringify` sink it
finds two script elements where the fixed sink finds one.
