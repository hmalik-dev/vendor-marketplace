# Schema review

Review of the 28 tables in `packages/db/src/schema/*.ts`, checked against the newest snapshot `packages/db/drizzle/meta/` and against the writers and readers in `apps/api/src`, `apps/web/src` and `packages/db/src/scripts`.

Every table ends `.enableRLS()`: row-level security is **enabled, not forced**. The table owner (the role the API connects as) bypasses it, and so does any role with `BYPASSRLS` (`neondb_owner` has it on `dev` and `staging`). Any other role sees nothing until a policy grants access. Enabling RLS is defence in depth. Authorisation is still done in the API.

Classes:

- **user-owned**: a row belongs to one customer or vendor.
- **public-read**: vendor profiles, reviews, categories and the rows that hang off a published profile.
- **operator-only**: admin actions, alerts, cases, settings, applications and invites.
- **system**: lookup and job tables.

Abbreviations: PK primary key, FK foreign key, NN not null, UQ unique index, partial = has a WHERE clause. FK actions are cascade, restrict or set null. Writers and readers are the DAO/service that holds the query; the web app reaches every table through the API.

## Differences from what the code assumes

- **Package price range** (fixed, VEN-508). `service_packages_price_cents_range` checks `price_cents` between `MIN_BOOKING_AMOUNT_CENTS` and `MAX_PACKAGE_PRICE_CENTS`, the band `priceCentsSchema` enforces, so a writer that skips the schema cannot store zero or a negative.
- **Typical guest count ordering** (fixed, VEN-508). `users_typical_guest_count_order` checks `typical_guest_count_min <= typical_guest_count_max`; a NULL on either side passes, as the Zod refinement allows.
- **Money and count columns** (fixed, VEN-550). `bookings_total_amount_cents_positive`, `bookings_platform_fee_cents_non_negative`, `bookings_vendor_payout_cents_non_negative`, `bookings_refund_amount_cents_range` (null, or `0 <= refund <= total`), `bookings_external_refund_cents_non_negative`, and on `booking_requests` `booking_requests_quoted_price_cents_non_negative`, `booking_requests_final_price_cents_non_negative`, `booking_requests_guest_count_non_negative` (null passes). `booking_requests_expiry_check_attempts_non_negative` (VEN-551, nullable counter of held expiries) follows the same rule, as does `booking_requests_payment_intent_replacements_non_negative` (VEN-547, `NOT NULL DEFAULT 0`: canceled intents replaced, the creation idempotency key's suffix; the migration adds the column with a constant default, so it rewrites nothing and no existing row can violate the check). Every writer was read first: payment (`calculateFees` on the amount Stripe received), cancellation (`calculateRefund`, and `reversalAmountCents` capped at the payout), account unwind and dispute (refund topped up to the total, never past the charge) and the seeds. The refund bound holds because foreign refunds live in `external_refund_cents`, not `refund_amount_cents`. **Dropped: none.** Legacy rows: read-only counts on `dev` and `staging` found 0 violating rows (both have 0 bookings; `external_refund_cents` is not yet on either branch and is `NOT NULL DEFAULT 0`). `production` cannot be read from a lane; the migration aborts atomically on a violating row and the deploy stops before the API moves. **Not a check: `platform_fee + vendor_payout = total`**, because a cancellation rewrites the payout to what the vendor keeps.
- **Foreign keys with no supporting index**, so deleting the parent row scans the child table (VEN-508). Six are indexed, three are deliberately not:

  | Column                            | Decision                         | Why                                                                                                                     |
  | --------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
  | `booking_requests.package_id`     | `booking_requests_package_idx`   | A vendor's packages are cascade-deleted with it and each one triggers the `SET NULL` scan of the largest request table. |
  | `messages.sender_id`              | `messages_sender_idx`            | User erasure cascades here; messages grow without bound.                                                                |
  | `reviews.reviewer_id`             | `reviews_reviewer_idx`           | The unique index leads with `booking_id`, so a user delete scanned the table.                                           |
  | `review_tombstones.reviewer_id`   | `review_tombstones_reviewer_idx` | The primary key leads with `booking_id`; same user-delete scan.                                                         |
  | `support_cases.sender_user_id`    | `support_cases_sender_user_idx`  | User erasure sets it null; cases accumulate per user.                                                                   |
  | `support_cases.resolved_by`       | `support_cases_resolved_by_idx`  | Same, for the resolving operator.                                                                                       |
  | `vendor_invites.invited_by`       | skipped                          | Invite-only beta table with a handful of rows, never joined or filtered on this column.                                 |
  | `platform_settings.updated_by`    | skipped                          | A single-row table (`PLATFORM_SETTINGS_ID`); a scan of one row is free.                                                 |
  | `tag_suggestions.resolved_tag_id` | skipped                          | Tiny moderation table and tags are never deleted in normal operation.                                                   |

## Checking RLS on a live database

```sql
select c.relname from pg_class c join pg_namespace n on n.oid = c.relnamespace
 where n.nspname = 'public' and c.relkind = 'r' and not c.relrowsecurity;
```

Zero rows means every table is covered. `rolbypassrls` on the connecting role decides whether a later `FORCE` can bind it at all (VEN-504: `true` for `neondb_owner` on `dev` and `staging`).
